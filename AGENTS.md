# Repository Guidelines

## Project Structure & Module Organization
`src/` contains the application and is organized by responsibility: `app/` the SongBird composition root and its songbird-only coordinators, `appcore/` the application services shared by both front-ends (`ProxySession`, core discovery and cleanup, TUN runtime, background-task coordination, runtime resolution), `auto/` the standalone SongBirdAuto front-end (a second application layer that reuses `appcore/`, `services/` and `runtime/` the same way `app/` does), `backends/` per-core config fragments and descriptors, `common/` small shared helpers, `domain/models/` config data types, `services/` business logic, `runtime/` core process and config writers, `subscription/` import/export parsers, `ui/` dialogs, models, tray, and main window, `persistence/` JSON config storage, and `platform/windows/` Windows-only integration.

Layering rules, enforced by `scripts/check-backend-boundaries.ps1`: `common/` may be included from anywhere; `backends/` must not include `app/`, `appcore/`, `ui/`, `services/`, or `platform/` (it may include `runtime/`); `app/`, `appcore/`, `auto/`, `ui/`, `services/`, and `runtime/` must not include `backends/`; and a front end — any directory containing a `main.cpp`, currently `app/` and `auto/` — is a top of the dependency order, so nothing below it may include it. The last rule is what keeps the shared layer from depending on one executable's code: `appcore/` used to reach up into `app/` for three headers, and every `appcore/` consumer inherited that dependency transitively. The check also refuses to pass if any directory containing a `main.cpp` is missing from its consumer list, so a new front end cannot escape the first rule by not being listed. Keep pure, I/O-free helpers in their own header (for example `auto/AutoCoordinatorLogic.h`, `auto/AutoCountryInference.h`, `common/EndpointParser.h`) so they can be unit tested without a live config file or process.

`tests/` mirrors these areas with Qt Test executables such as `MainWindowTests.cpp`, `JsonConfigRepositoryTests.cpp`, and `RoutingServiceTests.cpp`. `translations/` stores `.ts` files, `scripts/` contains packaging helpers, and `build/` is generated output and should not be edited by hand.

Sources are declared in three lists in `src/CMakeLists.txt`. `SONGBIRD_SHARED_SOURCES` holds everything both front-ends need; it is compiled once into the `songbird_shared_objs` OBJECT library, which `songbird`, `songbird_auto` and every test target link. `SONGBIRD_SOURCES` and `SONGBIRD_AUTO_SOURCES` hold only the leftovers for each executable. So a new shared source is registered in exactly one place — `SONGBIRD_SHARED_SOURCES` — and tests inherit it automatically; only a source used by a single front-end goes in that front-end's list. Test source lists in `tests/CMakeLists.txt` likewise carry only test-only files and the production files that are *not* shared.

`AppBootstrap::run()` is a composition root and must stay short: it calls the per-domain phases in order (`wireCoreServices`, `wireProxyStack`, `wireUiObjects`, `wireUpdateCoordinators`, `wireWorkflowCoordinators`, `wireServerCoordinators`, `wireShutdownHooks`) and then declares the startup tail as an ordered list of named steps on `StartupSequencer` (`common/StartupSequencer.h`), which executes them in order and stops at the first failing one. Steps are registered with `addStep()` (unconditional) or `addGate()` (returning false aborts the sequence and makes `run()` return false); `reload-config` is the only gate today. Add new startup work as a new step whose body is a small named `AppBootstrap` method (like `initializeTray`, `adoptManagedSystemProxyOnStartup`, `presentMainWindowOnStartup`, `scheduleAppUpdateChecks`) rather than inlining it in `run()`. Each phase lives in its own `app/AppBootstrap*Wiring.cpp` and may only construct `objects_` entries and inject callbacks — it must not touch the UI or start background work. Add new objects and callback wiring to the matching `*Wiring.cpp` rather than growing `run()`. Signal wiring for the main window, tray, proxy session and runtime state lives in `AppBootstrapMainWindowWiring.cpp`; keep new `QObject::connect` calls for those objects there instead of in `AppBootstrap.cpp`. Note that `AppBootstrap.cpp` and its `*Wiring.cpp` files belong to the `songbird` target only, not to `SONGBIRD_AUTO_SOURCES`.

The member order in `AppBootstrapObjects.h` is load bearing, not cosmetic. Members are destroyed in reverse declaration order, and each wiring phase hands earlier members into later ones — either as a `Dependencies { T& }` reference or as a `QObject* parent`. Both mean the constructed object must be destroyed before the member it borrows. Declaring such an object *above* the member it borrows makes `~QObject()` delete it first and the owning `std::unique_ptr` free it again, which is a double free at every shutdown. So: declare a borrowed member before its borrowers, and only append new members at the end. `scripts/check-appbootstrap-member-order.ps1` enforces this; references captured inside a lambda body are deferred uses and are deliberately ignored.

Work that runs off the GUI thread must not hold a raw pointer to a QObject the GUI thread can destroy. A continuation that captures `this` is only safe when it is posted to `this` (Qt then drops the call if the object is gone) or when it tests a lifetime token — `QMetaObject::invokeMethod(this, [this, guard]() { if (guard.expired()) return; … })`. The failure does not surface where the bug is: the continuation runs later against freed memory and the crash lands in whatever allocates that memory next. `scripts/check-async-owners.ps1` enforces both shapes.

Colours live in a palette file and nowhere else: `src/ui/theme/AppThemePalette.cpp` for the main window, `src/auto/AutoWindowPalette.cpp` for SongBirdAuto (which deliberately has a blue accent rather than the main app's green). A hex literal in a stylesheet branch is invisible to any runtime probe, because the probe only sees widgets that run constructed. `scripts/check-hardcoded-colors.ps1` enforces this, and the allowlist is an explicit two-entry file list rather than a `*Palette*` naming rule so a new file cannot opt out by being named helpfully.

A guard that cannot fail is worse than no guard, because it produces the appearance of coverage. `scripts/selftest-guards.ps1` mutates a throwaway copy of `src/` once per rule, asserts each guard goes red, and asserts all of them go green on the untouched copy — so a guard that rejects everything indiscriminately fails too. Add a case there whenever you add a rule.

A test executable that runs zero cases reports success: Qt Test counts `initTestCase`/`cleanupTestCase` as passes, so a suite whose `private slots:` lost its body prints `Totals: 2 passed` and exits 0. `scripts/check-test-suites.ps1` counts the real `PASS : Class::slot()` lines instead, and runs under `ctest -L suite` (it re-executes every test binary, so it stays out of the default run).

## Build, Test, and Development Commands
Use the checked-in CMake presets on Windows.

- `cmake --preset msvc-debug` configures a local Qt5 debug build.
- `cmake --build --preset msvc-debug --parallel` builds the app.
- `cmake --preset msvc-release` configures a local Qt5 release build.
- `cmake --build --preset msvc-release --parallel` builds the release app.
- `cmake --preset msvc-debug -DBUILD_TEST=ON` reconfigures the debug build with test targets enabled.
- `cmake --build --preset msvc-debug --parallel` builds the enabled test targets.
- `ctest --test-dir build/msvc-debug --output-on-failure` runs the full Qt Test suite.
- Releases are built and published by GitHub Actions, not locally: pushing a `v*` tag runs `.github/workflows/release.yml`, which installs the static Qt5, runs `ctest -LE smoke`, and calls `gh release create` with `songbird.exe`. The published asset is `SongBird.exe` only; `SongBirdAuto.exe` is not currently shipped in a release.

Requirements are CMake 3.24+, Ninja, MSVC with C++20, Qt 5, the `QT5_PREFIX_PATH` environment variable, and the vcpkg toolchain at `D:/vcpkg`.

`.cnb.yml` is the second CI system, and it deliberately does not mirror the Windows release build. It builds and tests on Linux against Debian's `qtbase5-dev` and runs the same `ctest -LE smoke`, because the question it answers is "does this change pass", not "does the release artifact look right" — publishing stays exclusively in GitHub Actions. Keep the two in step when a gate changes: a guard that exists only in `.github` is, in practice, a guard nobody sees fail.

The `scripts/check-*.ps1` guards and their self-test run on the GitHub runners only. PowerShell reaches Debian through Microsoft's apt source, and apt's `sqv` now refuses that source outright: its `InRelease` is signed by the same SHA1-self-signed key as its metadata, and re-signing policy rejects it since 2026-02-01, so `apt-get update` exits 100 and the job dies before it compiles anything. Adding the source's own key to `trusted.gpg.d` does not help either: the signature it would trust carries the same SHA1 self-signature the policy rejects. `tests/CMakeLists.txt` therefore registers those tests only when `find_program` finds `pwsh` or `powershell`, which is why a Linux `ctest` run reports fewer tests than a Windows one rather than a failure. Do not add a Linux stage that calls those scripts without solving the key first.

Building on Linux is not the same product. `platform/PlatformServices.h` resolves `PlatformAutoRunService` and `PlatformSystemProxyService` to `platform/null/` there, so the auto-run and system-proxy side effects degrade to stand-ins that report "not applied" rather than the composition root growing a per-platform conditional at each construction site. macOS keeps its real implementations; do not assume a new platform service only needs a Windows class.

Two things the Linux build taught, and both are rules now. A test that hard-codes a file name must match what the code derives — the state file is `<primary base name>.state.json`, and a hard-coded `SongBird.state.json` only ever passed because NTFS and APFS compare names case-insensitively. And a test that asserts on where a `QMenu` opens is asserting the display's size; `QMenu` flips and clamps itself, so on a shorter screen the popup legitimately moves. Assert the coordinate the widget was asked for, not the one Qt chose.

`LogItemDelegate::sizeHint()` measures the text at the width and with the metrics it will be painted with, rather than reading `LogListModel::LineCountRole`. The model's count is computed against the viewport width minus padding, which in a `QListView` is not the width a row is laid out at, and it is only as fresh as the last queued `setWrapConfiguration()` — both make a two-line row report one line and clip its second. The delegate is given the view through `setView()` for the same reason: a `QFontMetrics` built from the option's own font does not agree with the widget's, so the row would be sized by one number and drawn by another.

## Coding Style & Naming Conventions
Follow the existing C++ style: 4-space indentation, braces on their own line, `constexpr`/`QStringLiteral` where appropriate, and include ordering similar to `src/app/main.cpp`. Use `PascalCase` for classes (`CoreLifecycleService`), `camelCase` for functions and locals, and keep tests named `*Tests.cpp`. Prefer small, focused changes inside the relevant module instead of cross-cutting rewrites. There is no repo-local formatter config, so match surrounding code exactly.

## Configuration Persistence
The app uses `JsonConfigRepository` for configuration storage. The primary config path is supplied at runtime, commonly as a file such as `songbird.json`. Runtime/UI state is saved separately next to it using the primary file base name plus `.state.json`; for example, `songbird.json` pairs with `songbird.state.json`.

Primary config data is serialized through `JsonConfigSerialization` and related collection, policy, root, TUN, and UI serializers. State-only data is serialized through `JsonConfigStateSerialization`; this includes UI state such as selected tabs and column widths, plus per-server state such as `serverStates[].testResult`. Do not assume legacy names such as `guiNConfig.json` unless current code explicitly references them.

## Testing Guidelines
Tests use Qt Test through CTest. Add or update tests in `tests/` whenever logic changes in `runtime/`, `services/`, `subscription/`, `persistence/`, or UI behavior that already has coverage. Prefer descriptive test names that encode the behavior under test, following existing patterns such as `generateClientConfigsAdds...`. Reconfigure `msvc-debug` with `-DBUILD_TEST=ON` and run `ctest --test-dir build/msvc-debug --output-on-failure` before submitting changes, unless the current task explicitly says not to run tests.

README screenshots live in `docs/screenshots/` and are referenced by relative path. `scripts/check-readme-assets.ps1` scans every `README*.md` and verifies each referenced image exists and is non-empty, because nothing compiles the README and a moved screenshot otherwise leaves a broken icon on the project's front page. Whether a screenshot still matches the current UI cannot be automated, so the rule is a human one: when a change alters the main window's layout or the settings dialog's tabs, update the images in the same commit. Take them from a real run of the built binary with a demo config (no core, `--skip-core`), and crop out the log panel and status bar — those show machine-specific paths that must not appear in a public repository.

`README.md` is the English page and `README_zh_CN.md` is its Simplified Chinese counterpart; each links to the other at the top. Both are maintained by hand and share the screenshots, so a change to the feature list, the download table or the protocol matrix belongs in both in the same commit. The translated page is not generated, and nothing verifies that it still matches the English original — that needs a reader of both languages, so treat "update the other README" as part of the change rather than as a follow-up.

## SongBird Runtime Rules
Treat proxy activation as a staged state machine owned by `AppBootstrap::RuntimePhase`: `EnvironmentCleanup`, `ValidateCoreApplication`, `ValidateCoreConfig`, `ValidateRuntimeResources`, `StartTunRuntime`, `StartCoreProcess`, `CheckOutboundConnection`, and `ApplySystemProxy` lead to `Proxying` or `Stopped`. The core config is validated before the runtime resources because generating the runtime config needs the resolved core info and rule-set validation parses that generated config. Keep user-facing startup checklist wording and runtime phase transitions aligned when changing startup behavior.

A node probe that never ran is not a failure. `AutoNodeEvaluation::inconclusive` marks the case where no core was started -- a temporary port could not be reserved after several attempts -- and `mergeEvaluationResults()` skips those instead of feeding them to `RoutingScorePolicy::recordResult()`. A busy port says nothing about the node, so scoring it as a failure pushed the circuit breaker's counter toward tripping healthy nodes, which showed up as "a good node went red" with no explanation in the log.

Node selection goes through the policy's switch decision. Both places that move the connection -- `maybeSwitchToBestServerAfterEvaluation()` and `switchToNextBestSameCountry()` -- ask `AutoCoordinatorLogic::shouldMoveActiveServer()` when a challenger exists; a country with no alternative left refreshes its subscriptions instead, because which-node is not a question the policy can answer without a second node. The gate forwards to `RoutingScorePolicy::shouldSwitch()`. The best-ranked node is often only milliseconds ahead and switching costs a core restart, so the margin, the minimum hold window and the breaker all have to apply; do not go back to comparing ranks, and do not inline a margin or a cooldown timer in the coordinator. The policy is the only place those three can be tested without a running core.

The active node is `activeServerIdFor(config, activeServerId_)`: the node this session actually started, falling back to `config.currentIndexId` before the first start. Comparing a challenger against an empty id is how the first round after launch went by without applying anything, and comparing against the saved selection when a start has happened would compare against a node that is not carrying traffic.

The minimum hold window is what makes the margin sufficient. `RoutingScorePolicy::Config::minimumHoldMs` (10 minutes) keeps a node that started recently regardless of how much better a challenger is, because a margin alone still switches whenever a genuinely faster node appears -- and a subscription that rotates its nodes every minute would then restart the core on every round. A tripped current node ignores the window: it is failing, not merely not optimal. The coordinator arms the window when the session actually comes up (`ProxySession::activated`), not when the user clicked, and resets it on stop, on `finishStopped()` and in `clearEvaluationState()`.

A failed health check is evidence, so `switchToNextBestSameCountry()` feeds it to the policy as a failure before asking whether to move. That is what keeps failover bounded without a separate timer: the first failed check holds, the third trips the breaker, and a tripped node is replaced without a margin.

The outbound is checked in two layers, and they must not be mixed. `OutboundLivenessProbeService` is the gate: a `generate_204` host answering through the local proxy is what decides `reachable`, and it is the only outbound signal startup may fail on. `OutboundLocationProbeService` is display only -- it runs after the session is already `Proxying`, and a failure there writes a log line and a status-bar warning and nothing else. `computeProxyUiState()` reports `Active` only when the runtime is `Proxying`, the core is ready, the system proxy is enabled, and the outbound was confirmed reachable (`ProxySession::outboundReachable()`). Do not relax that to make the toolbar appear active, and do not put the location string back into the decision.

Runtime UI state should flow from `RuntimeStateSnapshot`. `AppBootstrap::syncStatusIndicators()` builds the snapshot, `RuntimeState::applySnapshot()` emits `snapshotApplied`, and `MainWindow::applyRuntimeState()` updates the UI from that full snapshot. Avoid adding new independent MainWindow booleans for core/proxy state; extend the snapshot or `ProxyUiState` instead.

The START/STOP toolbar state is derived through `ProxyToolbarController` from `ProxyUiState`, TUN state, existing cores, and the active server. Avoid direct `QAction` state edits for proxy controls outside the controller, and do not feed the exit location back into it: the location is display only.

Proxy startup blocks background work. `BackgroundTaskCoordinator` uses `AppBootstrap::isProxyActivationInProgress()` as its blocking predicate, covering the activation phases through `ApplySystemProxy`. New subscription updates, speed tests, imports, or core/resource updates must respect this coordinator instead of bypassing it.

Subscription parsing is a chain of parsers, and the chain has invariants the tests pin. `SubscriptionContentParser::parseManyWithReport()` walks from the outer encoding inwards — share URLs, sip008, sing-box, Clash, then one more base64 decode — and stops at the first parser that produces an item. `ClashSubscriptionParser::parseContent()` reads a document that parses as JSON *as JSON* and only falls back to the line-based `ClashYamlProxyParser` otherwise: JSON is valid YAML, so the walker used to read it partly (`proxies:` loses its value, the flow items are not list items, an inner `"server":` becomes a top-level key) and the fallback was then unreachable whenever the document also carried `proxy-groups:` or `rules:`.

The YAML walker builds every node from its own key/value pairs and rebuilds the `QJsonObject` per node. Do not reintroduce a shared or reused object: `QJsonObject::insert()` drops a null key, so a `type:` written with no value leaves the *previous* node's type in a reused object and the node parses as a supported protocol carrying somebody else's address. A malformed flow item (`- { name: broken, type: trojan` with no closing brace) is a fragment, not a node: its remaining block-style fields are dropped rather than glued on, and the entry is reported once as `(malformed flow item)`.

`SubscriptionYamlParser::splitKeyValue()` and `stripComment()` are both quote-aware, and neither may go back to a bare `indexOf`: `name: "a: b"`, `server: "[2001:db8::1]:443"` and `name: "Gemini #1"` are values, and cutting them is how a node disappears without a trace. A `:` only separates when it is followed by whitespace, which is also what keeps an IPv6 literal on the value side.

`skippedTypes` is the union of what every pass saw and could not use, not the last pass's list, so a subscription full of unsupported protocols says which protocols. `skippedSummary()` is the user-facing prose (`skipped 2 node(s): hysteria "h1"`) and `notes` is the diagnostic (`pass 0 clash count=0`, the decoded base64 prefix); `appendSkippedSummary()` and `appendParseNotes()` place them in that order, on separate lines, because the empty server panel shows the first line only. `notes` must never grow a line the user is meant to act on, and a decoded payload that is not text is described by its size rather than printed.

A parse failure is not a download failure. `failStreak` measures whether the URL answers, so a `200` whose body the parsers reject resets it instead of incrementing: retrying returns the same bytes, and counting it marked a reachable subscription unstable after three updates, which is a claim the log could not support.

Subscription updates are conditional and retried. `SubscriptionUpdateService` sends `If-None-Match`/`If-Modified-Since` from the subscription's persisted `etag`/`lastModified` and treats a 304 as a success that keeps the existing server list; a download that fails is retried up to three times with a short back-off before `failStreak` is incremented and saved, and any success resets `failStreak` to zero. Keep the interruption checks inside the retry loop — a shutdown must still be able to exit between attempts.

The IE/WinINET bypass list is one resolver in `common/SystemProxyExceptions`, called by both front ends. It used to be a byte-identical literal in `SystemProxyCoordinator.cpp` and `SongBirdAutoCoordinator.cpp`, and the two call sites then diverged -- the main app merged the hosts the routing rules send direct, Auto did not -- so a `direct` rule bypassed the system proxy in one executable and went through it in the other, for the same config file. Keep `routeDerived()`'s direction: a `direct` rule adds an entry, a `proxy` rule never does.

Node deduplication and export live outside `SubscriptionService`. `subscription/NodeFingerprint.h` is a deliberately coarse identity key (`configType + address + port + credentials`, ignoring remarks and transport wrapping) used to spot the same endpoint advertised by two subscriptions; it is not the same thing as `SubscriptionService::serverReuseKey()`, which is fine-grained so a refresh can carry a saved test result across to the matching node. `services/ExportService` builds share URIs and a Clash `proxies:` block via `subscription/ClashYamlBuilder`, and its dedup pass keeps the first occurrence in list order. Do not merge the two key functions: broadening `serverReuseKey()` would silently drop test results on refresh, and narrowing `NodeFingerprint::compute()` would let duplicates through export.

Auto node selection is scored, not just latency-sorted. `appcore/RoutingScorePolicy` is a pure decision table holding three mechanisms that answer different questions: an EWMA (`alpha`, default 0.35) so one slow probe does not reorder the list, a circuit breaker (3 consecutive failures, 60 s cooldown) so a node that is currently failing cannot win on a stale good score, and a switch margin (25 %) so two nodes within noise of each other do not trade the active connection on every probe. `SongBirdAutoCoordinator` keeps one `NodeState` per server in `nodeScores_`, feeds every completed probe into `recordResult()`, and ranks through `bestAutoServerIdForCountryByScore()`. A fourth knob, `minimumHoldMs` (10 minutes), delays switching to a genuinely better node, which the margin alone does not: see the node-selection rule above. The old `bestAutoServerIdForCountry()` survives as a thin wrapper that feeds raw latencies in as scores, so there is exactly one selection loop; do not reintroduce a second copy. `nodeScores_` must be cleared wherever `evaluations_` is cleared — a recycled `indexId` would otherwise inherit another server's smoothed latency and breaker state.

Batch export is split across three layers, and the split is what keeps each testable. `services/ExportService` owns the operations (`exportUris`, `exportClashYaml`, `deduplicate`) and is stateless. `MainWindow` owns the selection, the save dialog and the write — it takes the formatter as an injected provider via `setShareLinksExportProvider` / `setClashYamlExportProvider`, so `ui/` never includes `services/ExportService`. `AppBootstrap` is the only place that resolves the selected ids against the live config and calls the formatter, because it is the only layer that has both. Adding an export format means a new provider plus a new action; it must not mean teaching the window about `VmessItem`.

Subscription batches are ordered, not parallel. `services/SubscriptionUpdateOrder` reorders the batch before the serial loop walks it: subscriptions sharing a host are spread across round-robin passes so one host does not see a burst, and entries with a higher `failStreak` are deferred so a dead URL does not delay the healthy ones. `updateInternal()` stays serial on purpose — `config` is shared mutable state and parallelising it is a much larger change than the ordering. Do not add a `QSemaphore` concurrency gate without also making `config` access safe.

The terminal proxy is a separate side effect from the system proxy. `platform/ITerminalProxyService` manages `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY`, which is what curl, git, npm and pip read — the WinINET system proxy does not cover them. Its `capture()`/`restore()` contract is the same three-state one as `ISystemProxyService` (absent vs present-and-empty vs present-and-set), and `platform/TerminalProxyPolicy` holds the pure decisions: the URL written, the default bypass list, and the two "is this value ours?" checks. Writing must update both the registry and the in-process environment (`SetEnvironmentVariableW`), because Windows copies the parent's environment at `CreateProcess` time; the `WM_SETTINGCHANGE` broadcast uses `SendMessageTimeoutW` so a hung window cannot block shutdown. `NO_PROXY` is only written when the user has none, and is never deleted on disable — it usually holds the user's own bypass list.

**The terminal proxy is implemented but deliberately not wired into the app.** Nothing constructs `WindowsTerminalProxyService`: there is no settings checkbox, no call on proxy start or stop, and no snapshot persisted to `.state.json`. It ships as a library plus tests so the dangerous half — writing global environment variables — is verified before any user-facing switch exists. Wiring it means, at minimum: a `terminalProxyEnabled` config field, a General-page checkbox with copy explaining that an already-open terminal keeps its old environment, a decision in `evaluateSettingsDialogApplyPlan()` (enabling it must not restart the core), a member in `AppBootstrapObjects`, calls beside the system-proxy apply/restore points, and a startup check for a value a killed session left behind. Do not add the checkbox alone and call it done.

`HealthStripPolicy` is half wired: the history is persisted, the strip is not displayed. `VmessItem::healthStrip` holds the encoded 24 cells, `JsonConfigStateSerialization` reads and writes it beside `testResult` (decoded through the policy, so a malformed value becomes an empty history rather than a wrong one), and nothing draws it yet -- the server table has no strip column and no probe result is fed into `appendAndPrune()`. Persisting first is deliberate: the history is the slow half (a strip is worthless until it has accumulated hours), so the file format and its pruning/eviction semantics are settled and exercised by `JsonConfigRepositoryTests` before a column depends on them.

The 24-hour health strip is a pure fold, not a new data store. `appcore/HealthStripPolicy` turns probe records into 24 hour cells (oldest first), where `+1` means every probe in that hour passed, `-1` means at least one failed, and `0` means untested. Worst-in-hour is deliberate: an hour that was mostly fine but had an outage is an hour the node was unusable. Records older than the window and records dated in the future are both dropped rather than clamped, and `decode()` rejects malformed input outright — including a string that is not exactly 24 cells, because the cells are labelled by hour and a shorter or longer strip would label them wrongly. A strip showing the wrong history is worse than no strip, because the user would trust it.

The application version has exactly one declaration. `project(SongBird VERSION x.y.z)` in `CMakeLists.txt` is the source; `SONGBIRD_VERSION_SUFFIX` carries a prerelease label and `SONGBIRD_DISPLAY_VERSION` composes the two. `scripts/check-version-consistency.ps1` enforces that the composition is still the literal `${PROJECT_VERSION}${SONGBIRD_VERSION_SUFFIX}`, that `src/` and `scripts/` carry no second literal spelling of the version, and — when the release workflow passes `-Tag` — that the tag agrees with the declaration. Do not hardcode the version anywhere else; `tests/` is exempt because a version-comparison test needs concrete numbers as test data.

Core child processes are assigned to a Windows Job Object. `platform/windows/WindowsJobObject` creates one process-lifetime job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, and `QtCoreProcessHost` assigns each started child to it, so a SongBird crash takes the cores down with it. The handle is created once and deliberately never closed — closing it kills every assigned core. Assignment is best-effort and its failure is folded into the started log line; the PID file and `CoreProcessCleanupService` remain the fallback for a child that escaped the job.

Shutdown must be bounded. Background workers are tracked by `appcore/BackgroundThreadTracker` and stopped through `common/ThreadShutdown.h`, which escalates — request interruption, a short cooperative wait, a durable record plus a longer wait, then give up — inside a hard cap rather than waiting forever. `BackgroundThreadTracker::waitForAll()` reports whether every worker stopped; when one did not, the caller must not free anything that worker can still reach, because the tracked workers call `QMetaObject::invokeMethod()` on their owner and that dereferences it. The exit paths (`~ProxySession`, `~AppBootstrap`) therefore call `abandonProcessAfterStuckThread()` instead of unwinding. The record is appended to a file as well as the log stream, and is written before the process may die, because a GUI process's stderr is not visible to anyone and this line is the only clue a hung shutdown leaves behind. Budgets are constructor arguments so a test can drive the give-up path without waiting out the production cap.

## Settings And Platform Rules
Settings saves go through `evaluateSettingsDialogApplyPlan()` and `AppBootstrap::applySettingsDialogResult()`. Keep the dirty-plan model: unchanged settings should not be saved, and core restarts should be driven by the plan's runtime/TUN decisions rather than by a raw config-file comparison.

The system proxy has an ownership model, and it is not a boolean. `SystemProxySnapshot` (`common/SystemProxySnapshot.h`) records what `ProxyEnable` / `ProxyServer` / `ProxyOverride` / `AutoConfigURL` looked like *before* the first write of a session; `std::optional<QString>` is what distinguishes "the key did not exist" (restore = delete it) from "the key existed and was empty" (restore = write the empty value). The snapshot is captured once — just before the first write — and persisted to the `.state.json` companion, so a killed process can still put the user's own proxy back.

Both front ends wire the snapshot trio this way: the main app in `AppBootstrapServiceWiring.cpp`, SongBirdAuto in its coordinator's activation-coordinator setup. Auto's wiring additionally sanitises the capture (`sanitizeSelfReferentialSnapshot` — its only production caller) so a capture that sees this app's own dead port cannot record it as the user's value, and its startup runs `recoverSystemProxyFromPreviousRun()`: a registry that is on together with a valid persisted snapshot is a killed run's leftover and is restored; a registry that is on with no snapshot may be the user's own proxy and is left alone. Auto's restore reports failure when the service is absent rather than "nothing to do" — reporting success for a restore that never ran is what a half-wired trio silently does. The startup recovery is only sound while one Auto process exists: a second instance would treat the first's live proxy as a leftover. SongBirdAuto has no single-instance guard today; the TUN-elevation and port-conflict failures that stop a second instance in practice are not a lock, and adding a guard is a prerequisite for ever running two.

An exit has exactly one undo, and it is the session's. SongBirdAuto's destructor and `stop()` used to end at `updateSystemProxyMode(ForcedClear)` after `proxySession_->stop()` had already run the ownership undo — a second, snapshot-blind write over whatever that undo had just decided, so every exit ended at proxy off and the ownership decision was moot (issue #12). Do not add a clear after a stop on the theory that it is a fallback: a fallback has to be the *else* branch of a decision, and both of the ones that read as fallbacks in this tree are — `ProxySession::undoSystemProxyChange()` clears only when no snapshot survived, and the main app's exit clear runs only where `applyModeOnExit()`'s restore did not succeed. A write that runs after the decision regardless of it is not a fallback.

That deletion is pinned in two halves, and both are needed. `tests/ProxySessionTests.cpp` covers the session's side (an immediate stop performs exactly one registry operation), and `tests/SongBirdAutoCoordinatorStopTests.cpp` covers the coordinator's — it links the real coordinator, injects a recording `ISystemProxyService` through the constructor, and builds the session with `createProxySession()` instead of `initialize()`. Keep both arguments: the coordinator's service parameter defaults to the platform implementation so `main.cpp` is unchanged, and `createProxySession()` must stay callable without a config file or a core, because that is what makes the coordinator reachable from a test at all.

The rule that decides whether a teardown may touch the registry is ownership, never configuration: `decideFailedStartupProxyAction()` and `decideStopProxyAction()` in `appcore/SystemProxyOwnershipPolicy.h`. `config.sysProxyType` says what the user wanted and `isSystemProxyEnabled()` says the registry is on; neither says who turned it on, and using either one as evidence of ownership is what once made a failed startup delete a proxy the user had configured themselves. When ownership holds, prefer `restore(snapshot)` over `update(ForcedClear)`; clearing remains the fallback for when no snapshot survived. `update(ForcedClear)` is correct only when the user asked for the proxy to be off.

macOS reports `capture()` as invalid on purpose. Its proxy settings are per network service and the service list changes underneath a running app, so a faithful re-apply is not possible; the callers fall back to clearing, which is the pre-existing behaviour. Do not "fix" that by returning a synthesized snapshot.

TUN startup cleanup is part of environment cleanup. When TUN is enabled, stale `singbox_tun` adapter removal must happen before launching the managed core unless the environment has already been checked in the current startup flow. Preserve the cleanup/resume semantics when changing startup retry or crash-restart behavior.

UWP loopback support is a Windows platform tool, opened from Help, implemented by `UwpLoopbackDialog` and `WindowsUwpLoopbackService`. It must use `CheckNetIsolation.exe` for loopback exemptions, check availability before use, and use the elevated temporary-script path when SongBird is not already running as administrator.

Recent commits use concise, imperative summaries, for example `Data-driven Core tab with protocol-core compatibility filtering`. ## Security & Configuration Tips
Treat the primary config file such as `songbird.json`, its derived state file such as `songbird.state.json`, generated runtime configs, and Windows-specific settings as user data. Do not commit local secrets, subscription URLs, saved server test results, UI state, or machine-specific paths. Avoid manual edits under `build/`; regenerate through CMake instead.
